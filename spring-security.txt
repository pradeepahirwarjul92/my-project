public class CustomAuthenticationProvider
        implements AuthenticationProvider {

            Authentication auth) {

31. What is BCrypt?
BCrypt is a password hashing algorithm specifically designed for securely storing passwords.

Features
	-	One-way hashing algorithm
	-	Automatically generates a unique salt
	-	Configurable work factor (cost)
	-	Resistant to brute-force attacks
Note : BCrypt is a password hashing algorithm that combines hashing, salting, and an adjustable work factor to securely store passwords.	

32. Why is BCrypt preferred?
Ans - Because it is designed specifically for password storage.

| Algorithm | Good for Passwords?      |
| --------- | ------------------------ |
| MD5       | ❌ No                     |
| SHA-1     | ❌ No                     |
| SHA-256   | ⚠️ Not recommended alone |
| BCrypt    | ✅ Yes                    |

note : BCrypt is preferred because it automatically salts passwords and intentionally 
	hashes slowly, making brute-force attacks much harder.

| ---------- | ------------ | --------------- |
| Purpose    | Verification | Confidentiality |
| Reversible | ❌ No        | ✅ Yes          |
| Uses Key   | ❌ No        | ✅ Yes          |
| Output     | Hash         | Cipher Text     |
| Example    | BCrypt       | AES             |


34. What is salting?
Ans: A salt is random data added to a password before hashing.
Salting adds random data to passwords before hashing so that identical passwords generate different hashes.

59. What is Refresh Token?
A Refresh Token is a long-lived token used to obtain a new access token after the access token expires.

60. How do you revoke JWT tokens?

1. Token Blacklist
Store revoked token IDs (jti) or token hashes in a database or cache (such as Redis).

2. Short-lived Access Tokens
Issue access tokens that expire quickly (e.g., 15 minutes).

3. Refresh Token Rotation

Every time a refresh token is used:

Issue a new access token
Issue a new refresh token
Invalidate the old refresh token

This reduces the impact of a stolen refresh token.

4. Signing Key Rotation

Rotate signing keys when necessary. Tokens signed with retired keys can be rejected, though this may invalidate many active tokens depending on your strategy.

Maintain Refresh Tokens Server-side

Store refresh tokens (or their hashes) in a database and delete them during logout.

   ▼

   │
   ▼
User Cannot Obtain New Access Tokens

The browser automatically includes the user's session cookie, making 
the request appear legitimate

96. Why am I getting 401 Unauthorized?
A 401 Unauthorized error usually means authentication failed due to a missing, 
invalid, expired token, or because Spring Security couldn't establish an authenticated user.

97. Why am I getting 403 Forbidden?
A 403 Forbidden error means authentication succeeded, but authorization failed because 
the user lacks the required roles, authorities, or another security requirement such 
as a valid CSRF token.

98. JWT token is valid but request fails. Why?
A valid JWT alone is not enough. The request can fail because of incorrect authority mapping, 
missing Bearer prefix, expired claims, issuer/audience validation, or because the authentication 
was never placed into the SecurityContext.

	4. Security Disabled
	5. Incorrect URL Pattern
	6. Multiple SecurityFilterChain Beans
	
100. Spring Security application suddenly became slow. How would you troubleshoot?
Interview Answer

When a Spring Security application becomes slow, I first determine whether the delay occurs during authentication or authorization.
 I enable Spring Security debug logs, measure authentication latency, inspect 
 database queries in UserDetailsService, check password hashing cost, verify JWT 
 validation isn't making unnecessary remote calls, review custom filters for 
 expensive operations, analyze thread dumps and JVM metrics, and use profiling tools 
 to identify the bottleneck before optimizing the affected component.

6. How would you secure communication between microservices?
Ans : 
Securing communication between microservices involves ensuring that only

properly authenticated and authorized.

#1 Use HTTPS Everywhere
Never allow HTTP communication between services.

     │
     ▼

	-	Prevents packet sniffing.

        ▼

Benefits:

	-	Prevents unauthorized services from connecting.
	-	Encrypts communication.

Popular implementations:

	-	Service Mesh (e.g., Istio, Linkerd)
	-	Kubernetes with mTLS
	-	Spring Boot SSL configuration

7. How would you rotate JWT signing keys without downtime?
Answer : 
JWT signing key rotation is the process of replacing the private key used to sign JWTs without 
interrupting authentication for existing users.

The standard approach is to use multiple active keys with a Key ID (kid) in the JWT 
header and expose the public keys through a JWKS (JSON Web Key Set) endpoint. 
This allows services to validate tokens signed with both old and new keys during the 
transition.


# Why Rotate Signing Keys?
	-	Reduce the impact of key compromise.
	-	Meet security and compliance requirements.
	-	Support periodic key rotation.
	-	Minimize operational risk.
	
High-Level Architecture
                    Identity Provider
              (Keycloak/Okta/Auth Server)

          Old Key (K1)      New Key (K2)
                │               │
                └──────┬────────┘
                       │
                JWKS Endpoint
                       │
      +----------------+----------------+
      |                                 |
      ▼                                 ▼
 Order Service                  Payment Service
      │                                 │
 Validates K1 and K2            Validates K1 and K2
 
Step-by-Step Zero-Downtime Rotation :
------------------------------------ :
Step 1: Generate a New Key Pair
Create a new public/private key pair.
Old Key  : K1
New Key  : K2
#Do not remove the old key yet.

Step 2: Publish Both Public Keys
Expose both keys via the JWKS endpoint.

Example:
{
  "keys": [
    {
      "kid": "K1",
      "alg": "RS256"
    },
    {
      "kid": "K2",
      "alg": "RS256"
    }
  ]
}

Resource servers can now validate tokens signed with either key.

Step 3: Start Signing New Tokens with the New Key
New JWT header:
{
  "alg": "RS256",
  "kid": "K2"
}
Existing tokens continue using K1 until they expire.

Step 4: Continue Accepting Old Tokens
Validation logic:
JWT received
      │
Read kid
      │
      ▼
Find matching public key
      │
      ▼
Validate signature

	-	kid = K1 → Validate with old public key.
	-	kid = K2 → Validate with new public key.
	
	
Step 5: Wait for Old Tokens to Expire
Example:
	-	Access token lifetime: 15 minutes
	-	Refresh token lifetime: 7 days

After the maximum lifetime of tokens signed with K1 has 
passed (or they are refreshed), the old key is no longer needed.

Step 6: Remove the Old Key
Once no valid tokens remain that were signed with K1, remove it 
from the JWKS endpoint and stop accepting it.

Example Timeline : 
Day 1
------
K1 signs tokens

Day 30
-------
Generate K2
Publish K1 + K2
Start signing with K2

Day 31
-------
Services validate K1 and K2

Day 38
-------
All K1 tokens expired

Remove K1
Only K2 remains


Common Interview Follow-up Questions
1. Why not replace the key immediately?

Because users still have valid JWTs signed with the old key. Removing the old key 
immediately would cause those tokens to fail validation, resulting in authentication 
failures.

2. Why are asymmetric keys preferred?
With algorithms like RS256, only the authorization server holds the private signing key.
 All microservices only need the public key to verify signatures, reducing the risk of 
 key exposure.

3. What happens if the private signing key is compromised?
		-	Generate a new key pair immediately.
		-	Stop signing with the compromised key.
		-	Publish the new public key.
		-	Revoke or invalidate affected tokens if your architecture supports 
				it (for example, through token revocation or short token lifetimes).
		-	Remove the compromised key from the JWKS endpoint once it is safe to do so. 


8. How would you implement logout with JWT?
JWT is stateless, so unlike session-based authentication, the server does not keep track 
of logged-in users. This means simply deleting the token on the client is not enough in 
all scenarios, especially if the token has not yet expired.

The logout strategy depends on your application's security requirements.

Why Logout is Different with JWT

Option 1: Client-Side Logout (Simple)

The client removes the stored JWT.

Login
   │
JWT Stored
   │
Logout
   ▼
Delete JWT

Example (JavaScript):

localStorage.removeItem("access_token");
localStorage.removeItem("refresh_token");

Pros

Very simple.
Fully stateless.
No server-side storage.

Cons

If the token is stolen before logout, it remains valid until it expires.


Option 2: Short-Lived Access Tokens + Refresh Tokens (Recommended)

This is the most common production approach.

Access Token
      │
15 minutes
      │
Expires

Refresh Token
      │
7 days

Logout flow:

Delete the access token.
Revoke or delete the refresh token on the server.
The user cannot obtain new access tokens.
The existing access token expires shortly afterward.

Advantages

Minimal server state.
Limits exposure if an access token is compromised.
Scales well in distributed systems.

Option 3: Token Blacklisting

Maintain a blacklist of revoked JWTs.

Logout
   │
JWT ID (jti)
   │
Store in Redis
   ▼
Blacklist

On each request:

Receive JWT
     │
Check Redis
     │
Blacklisted?
   /     \
 Yes      No
  │        │
Reject   Validate JWT

Example schema:

JWT ID: 8fa12...
Expires: 2026-06-30T10:30

Pros
	-	Immediate logout.
	-	Immediate revocation.
Cons
	-	Introduces server-side state.
	-	Additional lookup on every request.


Option 4: Refresh Token Revocation

Store refresh tokens in a database.

User Login
      │
Refresh Token
      │
Database

Logout:

Delete Refresh Token

When the access token expires, the user cannot refresh it and must log in again.

Option 5: OAuth2/OIDC Logout

With providers like Keycloak, Okta, or Azure AD:

User
   │
Logout
   ▼
Application
   │
Logout Endpoint
   ▼
Identity Provider

The Identity Provider:

Revokes refresh tokens.
Clears its session.
Optionally performs Single Logout (SLO) across applications.
