Difference between EXISTS and IN.
🔹 IN vs EXISTS (Key Difference)

Both are used for subqueries, but they work differently.

✅ 1. IN

Checks whether a value exists in a list of values returned by a subquery.

SELECT emp_id, emp_name
FROM ms_employee
WHERE dept_id IN (
    SELECT dept_id
    FROM department
    WHERE location = 'Delhi'
);
✔ How it works:
Subquery runs first
Returns a list of values
Outer query compares each row against that list
⚠ Best for:
Small result sets
When subquery returns few distinct values
✅ 2. EXISTS

Checks whether the subquery returns at least one row (true/false check).

SELECT e.emp_id, e.emp_name
FROM ms_employee e
WHERE EXISTS (
    SELECT 1
    FROM department d
    WHERE d.dept_id = e.dept_id
      AND d.location = 'Delhi'
);
✔ How it works:
Subquery is executed per row
Stops immediately when a match is found
⚠ Best for:
Large datasets
Correlated conditions
When you only need existence check
🔥 Key Differences
Feature	IN	EXISTS
Type	Value comparison	Boolean check
Subquery	Usually non-correlated	Often correlated
Execution	Gets full result set	Stops at first match
Performance	Slower for large data	Faster in large joins
NULL handling	Can behave unexpectedly	Safer with NULLs
🚀 Simple Interview Line
IN = compares values
EXISTS = checks existence of rows
🎯 When to use what?
Use IN → small static list or small subquery result
Use EXISTS → large tables, correlated checks, performance-critical queries

What is CONNECT BY?
What is CONNECT BY in Oracle?

CONNECT BY is used to query hierarchical data (parent-child relationships) such as:

Employee → Manager
Category → Subcategory
Organization structure
Bill of Materials (BOM)

It recursively traverses rows in a hierarchy.

Example Table
emp_id	emp_name	manager_id
1	CEO	NULL
2	Manager A	1
3	Manager B	1
4	Employee X	2
5	Employee Y	2
6	Employee Z	3
Basic Syntax
SELECT emp_id,
       emp_name,
       manager_id
FROM ms_employee
START WITH manager_id IS NULL
CONNECT BY PRIOR emp_id = manager_id;
Explanation
START WITH → Root node (CEO)
CONNECT BY → Defines parent-child relationship
PRIOR → Refers to the parent row
Output
CEO
 ├─ Manager A
 │   ├─ Employee X
 │   └─ Employee Y
 └─ Manager B
     └─ Employee Z
LEVEL Pseudocolumn

Shows hierarchy depth.

SELECT LEVEL,
       emp_name
FROM ms_employee
START WITH manager_id IS NULL
CONNECT BY PRIOR emp_id = manager_id;

Output:

1	CEO
2	Manager A
2	Manager B
3	Employee X
3	Employee Y
3	Employee Z
Show Hierarchical Path
SELECT emp_name,
       SYS_CONNECT_BY_PATH(emp_name, ' -> ') AS hierarchy_path
FROM ms_employee
START WITH manager_id IS NULL
CONNECT BY PRIOR emp_id = manager_id;

Output:

CEO
CEO -> Manager A
CEO -> Manager A -> Employee X
CEO -> Manager A -> Employee Y
CEO -> Manager B
CEO -> Manager B -> Employee Z
Find Leaf Nodes

FROM ms_employee
WHERE CONNECT_BY_ISLEAF = 1
START WITH manager_id IS NULL
CONNECT BY PRIOR emp_id = manager_id;

Returns employees with no subordinates.

Avoid Cyclic Loops
SELECT *
FROM ms_employee
START WITH manager_id IS NULL
CONNECT BY NOCYCLE PRIOR emp_id = manager_id;

NOCYCLE prevents infinite recursion if circular references exist.

What is an index?
What is an Index?

An Index is a database object that improves the speed of data retrieval operations on a table.

It works like the index of a book:

Without an index → Database scans the entire table (Full Table Scan).
With an index → Database directly locates the required rows.
Example
Without Index
SELECT *
FROM ms_employee
WHERE emp_id = 1001;

Database may scan all rows.

Create Index
CREATE INDEX idx_emp_id
ON ms_employee(emp_id);

Now the database can quickly find emp_id = 1001.

Types of Indexes
1. Single Column Index
CREATE INDEX idx_emp_name
ON ms_employee(emp_name);
2. Composite Index
CREATE INDEX idx_dept_salary
ON ms_employee(dept_id, salary);

Useful for:

SELECT *
FROM ms_employee
WHERE dept_id = 10
AND salary > 50000;
3. Unique Index
CREATE UNIQUE INDEX idx_email
ON ms_employee(email);

Prevents duplicate values.

4. Bitmap Index (Oracle)
CREATE BITMAP INDEX idx_gender
ON ms_employee(gender);

Best for low-cardinality columns.

Advantages

✅ Faster SELECT queries
✅ Faster JOIN operations
✅ Faster ORDER BY and GROUP BY
✅ Improves query performance

Disadvantages

❌ Consumes storage space
❌ Slows INSERT/UPDATE/DELETE (index maintenance)
❌ Too many indexes can hurt performance

When Should You Create an Index?

Create indexes on:

Primary keys
Foreign keys
Frequently searched columns
Columns used in JOIN conditions
Columns used in WHERE clauses

Example:

SELECT *
FROM orders
WHERE customer_id = 100;

Index on customer_id is beneficial.

When Not to Create an Index?

Avoid indexes on:

Small tables
Frequently updated columns
Columns with very few distinct values (except bitmap indexes)
Check Execution Plan (Oracle)
EXPLAIN PLAN FOR
SELECT *
FROM ms_employee
WHERE emp_id = 1001;

View plan:

SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY);
Interview Answer (Short)

An Index is a database structure that improves query performance by allowing faster data retrieval. It reduces the need for full table scans but increases storage usage and DML overhead.

CREATE INDEX idx_emp_id
ON ms_employee(emp_id);
Key Interview Point

Indexes improve READ performance but can reduce WRITE performance because indexes must be updated whenever data changes.

What is a B-Tree index?
What is a B-Tree Index?

A B-Tree (Balanced Tree) Index is the most common index type used in databases such as Oracle Database, MySQL, PostgreSQL, and SQL Server.

It stores indexed values in a balanced tree structure, allowing the database to find rows efficiently without scanning the entire table.

Structure of a B-Tree
            50
         /      \
       20        80
      /  \      /  \
    10   30   60   90
Root Node → Starting point
Branch Nodes → Intermediate levels
Leaf Nodes → Store indexed values and pointers to table rows

Because the tree is balanced, searching is very fast.

Example
Create Index
CREATE INDEX idx_emp_id
ON ms_employee(emp_id);
Query
SELECT *
FROM ms_employee
WHERE emp_id = 1001;

Instead of scanning every row, the database traverses the B-Tree to locate the matching value.

Time Complexity
Operation	Complexity
Search	O(log n)
Insert	O(log n)
Delete	O(log n)

Without an index:

Full Table Scan = O(n)

With B-Tree:

Index Lookup = O(log n)
Best Use Cases
Equality Search
SELECT *
FROM ms_employee
WHERE emp_id = 1001;
Range Search
SELECT *
FROM ms_employee
WHERE salary BETWEEN 50000 AND 100000;
Sorting
SELECT *
FROM ms_employee
ORDER BY emp_id;
Prefix Search
SELECT *
FROM ms_employee
WHERE emp_name LIKE 'PRI%';
When B-Tree Index Works Well

✅ Primary Key columns

✅ Foreign Key columns

✅ Columns used in WHERE clauses

✅ JOIN columns

✅ ORDER BY columns

✅ Range queries

When B-Tree May Not Help
SELECT *
FROM ms_employee
WHERE emp_name LIKE '%KUMAR';

Leading wildcard (%) usually prevents efficient B-Tree usage.

B-Tree vs Bitmap Index
Feature	B-Tree	Bitmap
Best For	High-cardinality columns	Low-cardinality columns
DML Operations	Fast	Slower
OLTP Systems	Excellent	Poor
Data Warehouse	Good	Excellent
Example	emp_id, email	gender, status
Interview Answer (Short)

A B-Tree Index is a balanced tree-based index structure that stores keys in sorted order and enables fast searching, insertion, deletion, and range queries with approximately O(log n) complexity.

CREATE INDEX idx_emp_id
ON ms_employee(emp_id);
Key Interview Point

B-Tree indexes are the default index type in most databases and are ideal for equality searches, range searches, joins, and sorting operations.

What is a Bitmap index?
What is a Bitmap Index?

A Bitmap Index is a special type of index that uses bitmaps (0s and 1s) to represent the presence of values in a column.

It is most effective for low-cardinality columns (columns having few distinct values), such as:

Gender (M, F)
Status (ACTIVE, INACTIVE)
Marital Status
Yes/No flags

Primarily used in data warehouse and OLAP systems.

Example
Employee Table
Emp_ID	Gender
1	M
2	F
3	M
4	F
5	M

Bitmap representation:

Gender = M → 1 0 1 0 1
Gender = F → 0 1 0 1 0

To find all male employees, Oracle simply checks the bitmap:

1 0 1 0 1

which is extremely efficient.

Create Bitmap Index (Oracle)
CREATE BITMAP INDEX idx_gender
ON ms_employee(gender);
Query Example
SELECT *
FROM ms_employee
WHERE gender = 'M';

Oracle can use the bitmap index instead of scanning the table.

Multiple Conditions

Bitmap indexes are very efficient for combining conditions.

SELECT *
FROM ms_employee
WHERE gender = 'M'
  AND status = 'ACTIVE';

Example bitmaps:

Gender=M      : 1 0 1 0 1
Status=ACTIVE : 1 1 0 0 1
--------------------------------
AND Result    : 1 0 0 0 1

Bitwise operations are extremely fast.

Bitmap Index vs B-Tree Index
Feature	Bitmap Index	B-Tree Index
Best For	Low-cardinality columns	High-cardinality columns
Example	Gender, Status	Emp_ID, Email
OLTP Systems	Not recommended	Recommended
Data Warehouses	Excellent	Good
Concurrent Updates	Poor	Excellent
Storage	Smaller	Larger
Good Candidates for Bitmap Index
Gender      -> M/F
Status      -> Active/Inactive
Married     -> Yes/No
Country Code (few values)
Bad Candidates for Bitmap Index
Employee_ID
Email
Phone Number
PAN Number
UUID

These columns have many unique values (high cardinality).

Advantages

✅ Fast filtering

✅ Excellent for data warehouses

✅ Efficient multi-column queries

✅ Uses less storage

✅ Fast aggregations

Disadvantages

❌ Poor for frequent INSERT/UPDATE/DELETE

❌ Can cause locking/contention in OLTP systems

❌ Not suitable for highly transactional applications

Interview Answer (Short)

A Bitmap Index stores column values as bitmaps (0s and 1s) and is optimized for low-cardinality columns. It is commonly used in data warehouses for fast filtering and complex analytical queries.

CREATE BITMAP INDEX idx_gender
ON ms_employee(gender);
Key Interview Point
B-Tree Index → OLTP, high-cardinality columns
Bitmap Index → Data Warehouse, low-cardinality columns

Example: Use a Bitmap Index on gender, but use a B-Tree Index on emp_id.

How Do You Identify a Slow SQL Query?

A slow SQL query is identified by analyzing execution time, execution plans, resource usage, and database monitoring tools.

SET TIMING ON;

Oracle

SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY);

❌ Full Table Scan

❌ Cartesian Join

❌ High Cost

❌ Large Sort Operations

Example:

TABLE ACCESS FULL MS_EMPLOYEE

May indicate a missing index.

3. Check Actual Execution Statistics

Oracle:

SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL,NULL,'ALLSTATS LAST'));

Shows:

Actual rows
Buffers
CPU usage
Execution time
4. Find Long Running Queries
Oracle
SELECT sql_id,
       elapsed_time,
       executions,
       sql_text
FROM v$sql
ORDER BY elapsed_time DESC;

Shows the most expensive SQL statements.

5. Monitor Wait Events
SELECT event,
       total_waits,
       time_waited
FROM v$system_event;

Common waits:

DB File Sequential Read
DB File Scattered Read
Log File Sync
Row Lock Contention
6. Check Index Usage

Example:

SELECT *
FROM ms_employee
WHERE email = 'abc@test.com';

If execution plan shows:

TABLE ACCESS FULL

then an index may be missing.

Create:

CREATE INDEX idx_email

Look for:

FULL TABLE SCAN
HASH JOIN
NESTED LOOP (large tables)
SORT ORDER BY
SORT GROUP BY

These often contribute to slow performance.

8. Check Rows Processed

Bad example:

SELECT *
FROM orders;

Returns millions of rows unnecessarily.

Better:

SELECT order_id,
       order_date
FROM orders
WHERE customer_id = 100;

Useful performance reports:

AWR (Automatic Workload Repository)
ASH (Active Session History)

These help identify:

Top SQL by elapsed time
CPU-consuming SQL
I/O-intensive SQL
Blocking sessions

Available through Oracle performance tools and views.

INDEX RANGE SCAN

Step 2

tep 3

Q: How do you read an execution plan?

Answer:

Read the plan from bottom to top.
Identify access methods such as Full Table Scan, Index Scan, Hash Join, or Nested Loop.
Check Cost, Rows, and Bytes estimates.
Compare Estimated Rows (E-Rows) with Actual Rows (A-Rows) using DBMS_XPLAN.DISPLAY_CURSOR.
Focus on expensive operations like Full Table Scans, Sorts, and Hash Joins on large tables.
Use the execution plan to identify indexing, statistics, or SQL tuning opportunities.

37. How does an Index work internally?
Ans -An Index is a database object that helps Oracle find rows faster without scanning the entire table.

Think of an index like the index page of a book.

Without Index

Suppose a table has 10 lakh records.

SELECT *
FROM EMPLOYEE
WHERE EMP_ID = 500000;

Oracle may read every row until it finds EMP_ID = 500000.

Row 1
Row 2
Row 3
...
Row 500000 ✓
This is called a Full Table Scan.

Time Complexity:
O(N)


With Index
Create an index:
CREATE INDEX IDX_EMP_ID
ON EMPLOYEE(EMP_ID);
Now Oracle doesn't scan every row.

It uses a B-Tree Index (default index type in Oracle).
                500
              /     \
          <500      >500
         /   \      /   \
      100   300   700   900
	  
Oracle traverses the tree:
Root
 ↓
Branch
 ↓
Leaf
 ↓
Row Address (ROWID)
	  
Much faster than Full Table Scan.

Internal Structure of B-Tree Index

Root Block
    |
Branch Blocks
    |
Leaf Blocks
    |
ROWID

	a. Root Block
			Starting point of the search.
		EMP_ID < 500
		EMP_ID >= 500
	
	b.	Branch Block

			Narrows down the search.
		500 - 700
		700 - 900
		900 - 1000	
	
	c. Leaf Block	
			Contains:	INDEX_VALUE → ROWID
			Example: 	500000 → AAAABBBBCCCC
	
	ROWID 
		Oracle's physical address of a row.
			Data File
			Block Number
			Row Number
		Oracle uses ROWID to directly fetch the row.
