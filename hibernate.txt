Q1 - Difference: save() vs persist()
Ans 
| save()                    | persist()    |
| ------------------------- | ------------ |
| Returns ID                | No return    |
| Works outside transaction | No           |
| Hibernate specific        | JPA standard |

Q2 - get() vs load()
Ans - 
	| get()                     | load()           |
	| ------------------------- | ---------------- |
	| Returns null if not found | Throws exception |
	| Hits DB immediately       | Lazy proxy       |
	| Safe                      | Faster           |


Q3 - update() vs merge()
Ans - 
	| update()                          | merge()      |
	| --------------------------------- | ------------ |
	| Fails if object exists in session | Safe         |
	| Reattaches object                 | Copies state |

Q4 - Lazy vs Eager Loading
Ans -
| Lazy               | Eager             |
| ------------------ | ----------------- |
| Loads when needed  | Loads immediately |
| Better performance | Can slow system   |

Ans - Placeholder object used for lazy loading.

Q15 - 	Dirty Checking
Ans - 🧠 Key Idea

			👉 DB updated automatically

Q16 - What is Cascade in Hibernate?
Ans - Cascade = Automatic propagation of an operation from parent to child entities.
When you perform an action on a parent object (save, update, delete, etc.), 
Hibernate can automatically apply the same action to related child objects.
👉 Instead of managing each entity separately, Hibernate handles them together.

🧩 Types of Cascade in Hibernate
⭐ CascadeType.ALL

Applies all operations

PERSIST, MERGE, REMOVE, REFRESH, DETACH
⭐ CascadeType.PERSIST

Save operation only

⭐ CascadeType.MERGE

Update operation only

⭐ CascadeType.REMOVE

Delete children when parent deleted

⭐ CascadeType.REFRESH

Reload child state from DB

⭐ CascadeType.DETACH

Detach children from session

Ans - 	➡️ Multiple queries executed instead of one join query.
		➡️ Happens with lazy loading.

PRODUCTION SCENARIOS
=================================

Scenario 1:
Application is slow.

Check:
- Hibernate generated SQL
- Missing indexes
- N+1 queries
- Eager fetching

Enable:

spring.jpa.show-sql=true

=================================

Scenario 2:
LazyInitializationException

Reason:
Session closed before accessing lazy object.

Solution:

@Transactional

or

JOIN FETCH

=================================

Scenario 3:
N+1 Query Problem

Bad:

SELECT * FROM customer;
SELECT * FROM orders WHERE customer_id=1;
SELECT * FROM orders WHERE customer_id=2;

Solution:

JOIN FETCH

@EntityGraph

=================================

Scenario 4:
Connection Pool Exhausted

Check:

HikariCP metrics

Possible reasons:
- Long running transactions
- Unclosed sessions
- Database slowness

=================================

Scenario 5:
Entity Not Updated

Reasons:

- Missing transaction
- Detached entity
- Flush not executed

Use:

@Transactional

=================================

Scenario 6:
Duplicate Inserts

Reasons:

persist() called multiple times

Check:
equals() and hashCode()

=================================

Scenario 7:
Optimistic Lock Exception

Use:

@Version

Handle retries.

=================================

Scenario 8:
Memory Usage Increasing

Reasons:

Large persistence context

Fix:

session.clear()

batch processing
