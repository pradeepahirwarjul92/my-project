8. Difference Between EXISTS and IN
Ans Both EXISTS and IN are used to filter data based on another query, but they work differently.

Using IN

Find employees whose department exists in the DEPARTMENT table.

SELECT *
FROM EMPLOYEE
WHERE DEPT_ID IN (
    SELECT DEPT_ID
    FROM DEPARTMENT
);

How IN Works

Oracle first executes the subquery:


Using EXISTS
SELECT *
FROM EMPLOYEE E
WHERE EXISTS (
    SELECT 1
    FROM DEPARTMENT D
    WHERE D.DEPT_ID = E.DEPT_ID
);


Performance Difference
	IN
		WHERE EMP_ID IN (subquery)
		Executes subquery first.
		Compares values.
		Good for small result sets.
	
	EXISTS
		WHERE EXISTS (correlated subquery)
		Checks row-by-row.
		Stops when first match is found.
		Usually better for large tables.

34. Find the top 3 salaries in each department.


WITH dept_salary_rank AS
(
    SELECT e.*,
           DENSE_RANK() OVER
           (
              PARTITION BY dept_id
              ORDER BY salary DESC
           ) rnk
    FROM employee e
)
SELECT *
FROM dept_salary_rank
WHERE rnk <= 3;



35. Find the department with the highest average salary.

SELECT DEPT_ID,
       AVG_SALARY
FROM (
    SELECT DEPT_ID,
           AVG(SALARY) AS AVG_SALARY,
           DENSE_RANK() OVER (ORDER BY AVG(SALARY) DESC) DR
    FROM EMPLOYEE
    WHERE DEPT_ID IS NOT NULL
    GROUP BY DEPT_ID
)
WHERE DR = 1;


37. How does an Index work internally?
Ans -An Index is a database object that helps Oracle find rows faster without scanning the entire table.

Think of an index like the index page of a book.

Without Index

Suppose a table has 10 lakh records.

SELECT *
FROM EMPLOYEE
WHERE EMP_ID = 500000;

Oracle may read every row until it finds EMP_ID = 500000.

Row 1
Row 2
Row 3
...
Row 500000 ✓
This is called a Full Table Scan.

Time Complexity:
O(N)


With Index
Create an index:
CREATE INDEX IDX_EMP_ID
ON EMPLOYEE(EMP_ID);
Now Oracle doesn't scan every row.

It uses a B-Tree Index (default index type in Oracle).
                500
              /     \
          <500      >500
         /   \      /   \
      100   300   700   900
	  
Oracle traverses the tree:
Root
 ↓
Branch
 ↓
Leaf
 ↓
Row Address (ROWID)
	  
Much faster than Full Table Scan.

Internal Structure of B-Tree Index

Root Block
    |
Branch Blocks
    |
Leaf Blocks
    |
ROWID

	a. Root Block
			Starting point of the search.
		EMP_ID < 500
		EMP_ID >= 500
	
	b.	Branch Block

			Narrows down the search.
		500 - 700
		700 - 900
		900 - 1000	
	
	c. Leaf Block	
			Contains:	INDEX_VALUE → ROWID
			Example: 	500000 → AAAABBBBCCCC
	
	ROWID 
		Oracle's physical address of a row.
			Data File
			Block Number
			Row Number
		Oracle uses ROWID to directly fetch the row.	


Q - If there index is fast why we not create index on each columns
ans - Indexes improve SELECT performance but slow down DML operations.

Oracle must:
		Insert row into table
		Update all indexes

49. What is an Execution Plan?
Ans - An Execution Plan is the step-by-step strategy Oracle uses to execute a SQL query.

It shows:

How Oracle accesses data
Which indexes are used
Join methods used
Estimated cost
Expected number of rows

Before executing a query, Oracle's optimizer creates an execution plan.

50. How do you read an EXPLAIN plan?

EXPLAIN PLAN FOR
SELECT *
FROM EMPLOYEE
WHERE EMP_ID = 100;

SELECT *
FROM TABLE(DBMS_XPLAN.DISPLAY);

	* Important Rule
-	Read the Execution Plan from Bottom to Top	
	Many developers make the mistake of reading top to bottom.

| Operation             | Meaning               |
| --------------------- | --------------------- |
| TABLE ACCESS FULL     | Full table scan       |
| INDEX UNIQUE SCAN     | Exact index lookup    |
| INDEX RANGE SCAN      | Range lookup          |
| TABLE ACCESS BY ROWID | Fetch row using ROWID |
| NESTED LOOPS          | Join using loops      |
| HASH JOIN             | Join using hash table |
| MERGE JOIN            | Join sorted datasets  |
| SORT ORDER BY         | Sorting operation     |


51. Query takes 5 seconds on 50 million rows. How will you optimize it?
Ans - 
-	Analyze the execution plan.
-	Check for Full Table Scans.
-	Verify index usage and create appropriate indexes if needed.
-	Update optimizer statistics using DBMS_STATS.
-	Review join methods and filtering conditions.
-	Avoid unnecessary columns (SELECT *).
-	Consider composite indexes.
-	For very large tables, evaluate partitioning.
-	Measure before and after changes.
