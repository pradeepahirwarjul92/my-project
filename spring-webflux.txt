SPRING WEBFLUX - 100 QUESTIONS

BASICS

1. What is Spring WebFlux?
Ans- Spring WebFlux is Spring's reactive web framework that supports non-blocking, 
	asynchronous programming using Reactor (Mono and Flux).
2. Why was WebFlux introduced?

WebFlux was introduced to:

Handle large numbers of concurrent requests efficiently
Support non-blocking I/O
Improve scalability with fewer threads
Support reactive programming


3. Difference between Spring MVC and Spring WebFlux?
| Feature           | Spring MVC             | Spring WebFlux       |
| ----------------- | ---------------------- | -------------------- |
| Programming Model | Synchronous            | Asynchronous         |
| I/O               | Blocking               | Non-Blocking         |
| Thread Model      | One Thread per Request | Event Loop           |
| Return Type       | Object                 | Mono / Flux          |
| Scalability       | Moderate               | High                 |
| Server            | Tomcat                 | Netty, Tomcat, Jetty |


4. What is Reactive Programming?
Ans - Reactive Programming is a programming paradigm that handles data as streams of events and reacts to changes asynchronously.

Example:

Mono<String> mono = Mono.just("Hello");
Flux<Integer> flux = Flux.just(1,2,3,4);

5. What are the benefits of Reactive Programming?
Ans- 
Better scalability
Non-blocking execution
Efficient resource utilization
High throughput
Backpressure support
Responsive applications

6. What is Non-Blocking I/O?
Ans - In Non-Blocking I/O, a thread does not wait for an operation to complete.

Blocking
String data = service.getData(); // waits
Non-Blocking
Mono<String> data = service.getData();

The thread is free to process other requests.


7. What is Asynchronous Processing?
Ans - Asynchronous processing allows tasks to execute independently without blocking the caller.
Mono<String> result = webClient
    .get()
    .retrieve()
    .bodyToMono(String.class);
	
	The caller continues without waiting.
	
	
8. What is Event-Driven Architecture?

An architecture where components communicate through events.

Example:

Order Created
      ↓
Kafka Event
      ↓
Inventory Service
      ↓
Payment Service

Services react when events occur.

9. What problem does WebFlux solve?
Ans 
Traditional Spring MVC uses:

1 Request = 1 Thread

For thousands of concurrent requests:

Thousands of Threads
High Memory Usage
Thread Context Switching

WebFlux solves this by:

Event Loop
Non-Blocking I/O
Fewer Threads
Higher Scalability

10. When should you use WebFlux?
Use WebFlux when:

✅ High concurrency is required

✅ Microservices make many external API calls

✅ Streaming applications

✅ Real-time systems

✅ Reactive databases and messaging

✅ WebSocket applications

Avoid WebFlux when:

❌ Application is simple CRUD

❌ Uses blocking JDBC extensively

❌ Team lacks reactive programming experience

46. What is Scheduler?

A Scheduler determines on which thread a reactive pipeline executes.

Schedulers are similar to ExecutorService in Java.

| Scheduler        | Purpose             |
| ---------------- | ------------------- |

47. What is subscribeOn()?

subscribeOn() decides where the source starts executing.

Example
Flux.range(1,5)
    .subscribeOn(Schedulers.parallel())
    .map(i -> i * 10)
    .subscribe(System.out::println);
Flow
Source
  ↓
parallel Thread
  ↓
map()
  ↓
subscribe()
Key Point

Only the first subscribeOn() takes effect.


48. What is publishOn()?

Ans 
publishOn() changes the thread for all downstream operations.

Example
Flux.range(1,5)
    .publishOn(Schedulers.parallel())
    .map(i -> i * 10)
    .subscribe(System.out::println);
Flow
Source Thread
      ↓
publishOn()
      ↓
parallel Thread
      ↓
map()

49. Difference between publishOn and subscribeOn?
| Feature          | subscribeOn()        | publishOn()             |
| ---------------- | -------------------- | ----------------------- |
| Affects          | Source Execution     | Downstream Execution    |
| Position Matters | No                   | Yes                     |
| Multiple Calls   | First One Wins       | Every Call Works        |
| Purpose          | Change Source Thread | Switch Thread Midstream |

Example
Flux.range(1,5)
    .subscribeOn(Schedulers.single())
    .publishOn(Schedulers.parallel())
    .map(i -> i * 10)
    .subscribe();
Execution
Source
  ↓
single Thread
  ↓
publishOn
  ↓
parallel Thread
  ↓
map()


Interview Answer :

subscribeOn() affects where the subscription and source execution start, while publishOn() changes the execution thread for downstream operators. Only the first subscribeOn() is honored, whereas multiple publishOn() calls can switch threads multiple times.

50. What is boundedElastic Scheduler?
Ans - 
boundedElastic() is designed for blocking operations.

Examples
Database calls (JDBC)
File reading
Legacy APIs
External SDK calls
Example
Mono.fromCallable(() -> {
    Thread.sleep(5000);
    return "Data";
})
.subscribeOn(Schedulers.boundedElastic());
Why Not Use parallel()?

Bad:

Mono.fromCallable(this::blockingCall)
    .subscribeOn(Schedulers.parallel());

Blocking a CPU thread reduces performance.

Correct
Mono.fromCallable(this::blockingCall)
    .subscribeOn(Schedulers.boundedElastic());
Characteristics
Creates worker threads when needed
Reuses idle threads
Has an upper limit (bounded)
Prevents unlimited thread creation
Real Project Example
@GetMapping("/{id}")
public Mono<Employee> getEmployee(Long id) {

    return Mono.fromCallable(
            () -> employeeRepository.findById(id).get()
    )
    .subscribeOn(Schedulers.boundedElastic());
}
Interview Answer

boundedElastic() is a Scheduler intended for blocking I/O operations. It dynamically creates a bounded pool of worker threads and prevents blocking tasks from occupying event-loop or CPU-intensive threads. It is commonly used when integrating WebFlux with JDBC, file systems, or legacy blocking APIs.


BACKPRESSURE

51. What is Backpressure?
Backpressure is a mechanism that allows a consumer to control how much data it receives from a producer.

Problem
Producer → 10000 events/sec
Consumer → 100 events/sec

Consumer gets overwhelmed.

Solution

Consumer tells producer:

"Send only what I can process."

52. Why is Backpressure needed?
Without backpressure:

Memory overflow
OutOfMemoryError
Slow consumers crash
System instability
Example
Kafka Producer
    ↓
1,000,000 Messages
    ↓
Slow Consumer

Messages accumulate rapidly.

Benefits
Prevents overload
Improves stability
Controls resource usage

53. How does Reactor support Backpressure?
Reactor implements the Reactive Streams Specification.

The subscriber requests data explicitly.

Example
Flux.range(1, 100)
    .subscribe(new BaseSubscriber<Integer>() {

        @Override
        protected void hookOnSubscribe(Subscription subscription) {
            request(5);
        }
    });
Flow
Subscriber
    ↓
request(5)
    ↓
Publisher
    ↓
Send 5 Items

54. What happens when producer is faster than consumer?
Without Backpressure
Producer
  ↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓↓
Consumer

Problems:

Queue growth
High memory usage
Application crash
With Backpressure
Consumer
    ↓
request(10)
    ↓
Producer
    ↓
Send 10 Items

Producer waits for more demand.

| ----------------- | ---------------- | ------------ |
| Programming Model | Synchronous      | Reactive     |
| Thread Model      | Blocking         | Non-blocking |
| WebFlux Support   | No               | Yes          |
| Streaming Support | No               | Yes          |

66. How to handle WebClient errors?
Handle 4xx and 5xx

         .uri("/employees/1")
         .retrieve()

webClient.get()
         .uri("/employees/1")
         .retrieve()
         .bodyToMono(Employee.class)
         .onErrorResume(ex ->
                 Mono.just(new Employee()));

71. What is R2DBC?
R2DBC (Reactive Relational Database Connectivity) is a reactive API for relational databases.

It provides non-blocking database access similar to how WebFlux provides non-blocking HTTP communication.

Traditional
Application
    ↓
   JDBC
    ↓
 Database
Reactive
Application
    ↓
  R2DBC
    ↓
 Database
Benefits
Non-blocking
Reactive Streams compliant
Backpressure support
Suitable for WebFlux

72. Difference between JDBC and R2DBC?

| WebFlux Friendly            | No               | Yes          |
| Backpressure                | No               | Yes          |
| Reactive Streams            | No               | Yes          |

    return repository.save(emp);
}
Using TransactionalOperator
TransactionalOperator operator =

91. When should WebFlux NOT be used?
WebFlux is not the best choice in every situation.

Avoid WebFlux When
1. Application is CRUD-heavy with JPA/Hibernate
Spring MVC + JPA

is usually simpler.

2. Mostly Blocking APIs
JDBC
File IO
Legacy SOAP APIs

Reactive benefits are reduced.

3. Small Applications

For simple CRUD apps:

Spring MVC

is easier to develop and maintain.

4. Team Has No Reactive Experience

Reactive programming has a learning curve.

Interview Answer

WebFlux should be avoided when the application is primarily blocking, heavily dependent on JPA/Hibernate, or when scalability requirements do not justify the added complexity of reactive programming.
